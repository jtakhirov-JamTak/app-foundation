### 2026-08-02 — Server failures leave a controlled trace; detection and alerting stay deferred

**Before this, a 500 left nothing behind.** `apiErrorFromUnknown` returned a sanitized `{code, request_id, recoverable}` to the client and dropped the cause; `grep -rn 'console\.' src/` returned zero hits. Analytics only fire from _client_ error boundaries, so a server-side throw was invisible everywhere. It now emits one structured stderr line on any status ≥ 500, and `/api/events` logs its own `EVENT_WRITE_FAILED` inline because that 503 is returned via `apiError` directly and never reaches the shared logger. **Scope is deliberately traceable, not noticed** — no health endpoint, no uptime monitor, no error sink. Those remain required before app #2 launches, and ARCHITECTURE's _Explicitly Deferred_ entry was narrowed rather than deleted to say so.

**There is no message field, and its absence is the design.** Vendor and Postgres messages embed user data (playbook §6) — a Supabase or Stripe error routinely echoes the request body, and a Postgres `message`/`details`/`hint` can quote row content. The line carries `level`, `request_id`, `code`, and `error_type` only; the events route adds the Postgres SQLSTATE (`pg_code`) and nothing else. A code comment names the one sanctioned extension point: if a message is ever needed it enters through an explicit `safeLogMessage` field a caller consciously populates with a string it owns, never `error.message`. That field is not added now, because adding it speculatively is exactly what makes the next person reach for `error.message`.

**`SESSION_UNAVAILABLE` logs at `warn`, not `error`, and that split encodes a known conflation.** The rule started as a flat `status >= 500`. Reading `require-user.ts` against supabase-js showed why that was wrong: the only `AppError`s in production code are `UNAUTHENTICATED` (401) and `SESSION_UNAVAILABLE` (503), and an actually-expired session produces the **503**, not the 401 — `getClaims()` returns `{data: null, error: null}` when there is no session at all (→ 401, silent), but an expired or revoked _refresh_ token makes `getSession()` return an error, and an expired JWT makes `validateExp` throw `AuthInvalidJwtError`. Both land on 503. A flat rule would therefore emit an error line per request for every user whose session expired — an expected condition, on a PWA that background-syncs. Quiet-listing the code instead was rejected: it would go blind to a Supabase auth outage, which is the single most important server failure this trace exists to catch. `warn` keeps both. The residual problem is that one code still means two things — a single warn is an expired session, a sustained spike across many `request_id`s is a probable outage. **Splitting it into two codes is recorded here as a candidate for app #2's observability work**, where an error sink can aggregate warn-rate rather than relying on per-line severity; it was out of scope for a change whose point was the minimum trace.

**`digest` is optional and `recordError` spreads it rather than passing it.** `assertSafeEventProperties` iterates `Object.entries` and rejects any non-scalar, so a present-but-`undefined` key throws — and `digest` is `undefined` for every purely client-side error, i.e. the common path. `{area, code, recoverable, digest}` would have thrown in all three error boundaries. `...(digest ? { digest } : {})` is the only shape that survives, mirroring `trackScreen`'s existing `referrer_screen` idiom. `privacy.test.ts` now locks that exact failing condition rather than the fix. The key itself needed no new safety argument: `digest` was already in `ACCEPTED_KEYS` and in the SQL vector, so `db:test` would have passed without proving anything — what was missing, and was added, is the `app_error_recorded` fixture _carrying_ a digest.

**The typecheck hook is Stop, not PostToolUse, and parses its input with node, not jq.** Per-edit typechecking flags intentionally incomplete intermediate states mid-refactor and burns context on noise; a turn-boundary check runs once a coherent batch has landed. Exit 2 blocks the stop and feeds stderr back, which is what makes it self-correcting rather than informational. The documented loop guard reads `stop_hook_active` — real, though it lives in the hooks _guide_ troubleshooting section rather than the reference — and the documented example uses `jq`. **`jq` is not installed here and is not guaranteed on any derived app's machine**, and a missing `jq` makes the guard's test silently never fire: precisely the silent-exit class non-negotiable #9 exists to prevent. Node 22 is already a hard repo requirement, so the guard parses stdin with `node -e` and falls back to `false` on a parse failure — failing toward running the check, never toward skipping it quietly. Claude Code independently overrides a Stop hook after 8 consecutive blocks, so there is a backstop beneath the guard. `npm run verify` remains the hard gate; the hook is advisory speed. Accepted cost: a turn that only answers a question still pays the typecheck latency and can be blocked by breakage it did not introduce. **If it proves noisy in real use, delete it then, with that evidence** — not pre-emptively.

**LAUNCH BLOCKERS prints without failing, and `/deploy-check` is where it binds.** `release:verify` prints the checklist on both the pass and fail paths but never changes the exit code: these are human steps no script can prove, and gating automation on them would only teach people to skip the gate. Printing is not affirming, so `/deploy-check`'s human section now requires each line affirmed explicitly — PASS/FAIL/SKIPPED with a reason — before a derived app's first real users, with an unaffirmed line counting as FAIL.

### 2026-08-02 — Twenty-eight commands became thirteen; ARCHITECTURE keeps the numbers, DECISIONS keeps the narrative

**`.claude/commands/` went from 28 files to 13, and the cost being paid down was drift, not disk.** The reviewer-conventions preamble was copy-pasted into 12 files, `/full-review` and `/full-audit` and `/deploy-check scope=full` each re-described the same fan-out from a different angle, and five `/add-*` files repeated the same discover-first pass. Every duplicated paragraph is a place where two files can disagree and nothing catches it. Three merges absorbed seventeen files: `/add` takes a layer argument (endpoint/page/webhook/feature) over one shared discover pass; `/review` takes a mode (`changes`/`pipeline`/`repo`/`debt`); `/audit` takes an area (access/privacy/perf/deps/mobile/a11y/observability/db/ci).

**The accepted regression is context cost.** `/audit db` now loads all nine areas (~230 lines) where `db-check.md` was 101, and `add.md` historically carried a note saying the `/add-*` files were split precisely so invoking one layer didn't load the other four. That note is now false and was removed. Both merged files instruct "read **only** that section," which is mitigation, not a fix. If a future session finds an area being skimmed because the file is long, splitting that one area back out is the correct response — not reverting the merge.

**`.claude/REVIEWER_CONVENTIONS.md` folded into `ENGINEERING_PLAYBOOK.md` §11, which fixed a citation that had never resolved.** Seventeen citations across nine command files read `.claude/REVIEWER_CONVENTIONS.md §6`; that file was a flat five-bullet list with no numbered sections, so §6 never existed. All seventeen now read `.claude/ENGINEERING_PLAYBOOK.md` §11, which does. The playbook's §9/§10 inversion (§10 appeared before §9) was corrected in the same pass.

**ARCHITECTURE.md's Performance budgets shed ~1.2 KB of narrative that was already verbatim in this file.** The budget numbers stayed; what left was measurement prose — the 95/395/421 ms TBT batch, the 2143–2198 ms LCP spread, the ~130 ms preconnect drift, 268–408 ms across 19 runs, the ~6× headroom, the field-number-not-local-calibration rule, the `router.replace()` soft-navigation mechanism. Each clause was diffed against the entry it linked to before deletion; all but one were already present word-for-word, so this was removing duplication rather than relocating it. ### 2026-08-02 — Expensive proofs moved off the per-PR path onto a release gate

**Per-PR gates are now cheap and deterministic; expensive proofs run on `npm run release:verify`.** Three checks were demoted, and each was replaced rather than dropped — the point is where they run, not whether.

**`verify:sw-version-bust` is deleted, and `check:sw` is strictly stronger than what it replaced.** The script built three times (two synthetic versions plus a restore build) to prove cache names track `NEXT_PUBLIC_APP_VERSION`. One build proves it: `src/app/sw.ts` derives `cacheId` as `` `${appId}-${appVersion}` `` from two inlined literals, so the bundler constant-folds it to a single string in `public/sw.js`. `check-service-worker.mjs` now asserts that exact concatenation for the env the build ran with, and CI builds with a distinct `ci-<sha>` version every run, so a stale or hardcoded id cannot slip past. Verified by planting the failure, not by reading the code: built at `proof-v1`, then checked at `proof-v2` — exit 1 naming the expected id; checked with `NEXT_PUBLIC_APP_VERSION` unset — exit 1 refusing to pass vacuously. The old check compared `appId` and `version` as two independent substrings, which a hardcoded cache name containing both would have satisfied. `NEXT_PUBLIC_APP_VERSION` is now required by `check:sw` rather than optional; every caller already sets it. This resolves the `verify:sw-version-bust` simplification (P1) item formerly in **Explicitly Deferred** on its own stated terms — a cheap deterministic test, retained `e2e/service-worker.spec.ts` coverage, _and_ a release-only check.

**Lighthouse is release-only.** `lhci autorun` plus `check:lighthouse-url` are now `npm run perf:lab`, invoked by `release:verify`. Lab numbers are the least deterministic signal in CI and the slowest; the 2026-07-29 entry below already records that local TBT spans 95/395/421 ms in a single 3-run batch. The `check:lighthouse-url` guarantee from [`FIX_LOG.md`](FIX_LOG.md#2026-07-29--the-lighthouse-gate-never-measured-the-app-shell) is unchanged — it still runs immediately after `lhci`, still refuses to pass on an empty `.lighthouseci`. The fix-log entry says it is "wired into CI directly after `lhci`"; that stays as written and describes the code as it was, and this entry supersedes it.

**Per-PR e2e runs mobile-chromium only.** The accepted risk is recorded in ARCHITECTURE.md Trade-offs: a Safari-specific regression can sit on `main` between releases. Both engines run before any tag.

**The `performance-pwa` job is deleted outright, not rebuilt.** With lhci and the triple-build gone it held nothing unique: `quality` already runs `npm run build` then `check:sw` under the identical workflow env, and `mobile-e2e`'s Playwright run already includes `e2e/service-worker.spec.ts` under mobile-chromium — against a build made with real local-Supabase credentials, which is strictly more realistic. Keeping it would have cost a fourth runner and a duplicate build per PR for coverage that already existed.

**`release:verify` skips `verify:example-removal` on the example feature's absence rather than instructing derived apps to edit the script.** A doc note telling a scaffolder to delete a step is exactly the manual dependency this gate exists to remove; a forgotten edit would leave a derived app's release path permanently red.

### 2026-08-01 — Event semantics live in one zod catalog; the database enforces only generic invariants

**Event semantics had three definitions and now have one.** They were TypeScript interfaces in `catalog.ts`, a loose runtime schema in `schemas.ts` that accepted any `^[a-z][a-z0-9_]{0,63}$` name with any scalar record, and an 80-line `analytics_event_valid()` plpgsql function that every migration adding an event had to re-declare in full — `202607210002_example_records.sql` copied 86 lines of it to add one event, and `check-analytics-contract.mjs` grepped migrations to keep the copies in sync. `catalog.ts` is now zod-first: schemas define the enums and each event's `.strict()` properties, `eventPropertySchemas` keys the map, and `EventName`, `EventProperties`, `ScreenName` and the `/api/events` discriminated union are all `z.infer`red from it. The map rather than a flat union is what preserves per-event property typing for `trackEvent`; `catalog.test.ts` holds a never-invoked function with one valid call and one `@ts-expect-error` cross-event call, so `npm run typecheck` — not a reviewer — is what keeps that mapping.

**The database keeps only what survives any catalog:** name format, object-typed properties, scalar values, 4 KiB, and `analytics_properties_safe()`. The trade is deliberate — the DB stops rejecting a semantically wrong event, so the write path is closed instead of trusted: `events` has no RLS policy and no client insert grant, and `/api/events` writes with the service role after `requireUser()`. A client that bypasses TypeScript now reaches a route that parses the union, not a table.

**The sensitive-key regex rejects `screen_name` on purpose.** Matching on word boundaries (`(^|_)name(_|$)`) rather than bare substrings lets `subtitle`, `notes_count` and `hostname` through, which the old substring rule blocked. It still rejects every `*_name` segment including technical-sounding ones, because enumerating the acceptable variants is an unwinnable blocklist — `child_name`, `partner_name`, `doctor_name`. The answer is to rename the key at catalog-design time (`screen`, `metric`, `code`). The risk that inverts is a false positive rejecting a legitimate event, so pgTAP inserts one valid instance of every catalogued event: a future policy change that breaks one fails `db:test` instead of failing silently in production. The same accept/reject vectors are asserted in `privacy.test.ts` and in SQL — that pairing is the cross-language contract.

**Declaration merging was dropped, not replaced.** `keyof typeof` over a const map and `z.infer` enums cannot be augmented, so `_feature/analytics-extension.ts` and `registerScreenPath` are gone and the catalog is extended by editing it. The example feature's entries sit in `EXAMPLE-ONLY` blocks in `catalog.ts` and `screen-registry.ts`, which `verify:example-removal` strips in a throwaway copy.

**That hand-maintained `MARKED_FILES` list is only as safe as what fails when it is wrong, so each direction has its own guard — established by planting each mistake and confirming the exit code, not by reading the script.** A marker in a file nobody listed is caught by the repo-wide marker scan over `src/`, `supabase/` and `e2e/` (exit 1). A listed block that _loses_ its markers splits in two: if the leftover dangles it is caught by `typecheck` (exit 2) — an orphaned `eventPropertySchemas` entry referencing a stripped schema, a `screen-registry` tuple the stripped enum no longer admits — but a **self-contained** leftover such as `"example"` in an enum compiles, tests and ships silently, so `FORBIDDEN_LITERALS_AFTER_STRIP` checks the quoted literals directly (exit 1). It is token-specific rather than a repo-wide `/example/i` scan because the pgTAP fixtures and e2e specs legitimately use `@example.invalid` addresses. SQL needs no marker at all: the example's analytics fixture row lives in `src/app/(app)/(example-feature)/_tests/example-rls.sql`, deleted wholesale with the folder — structural co-deletion, which is why it is preferred over a guard wherever the layout allows it. That matters here because `verify:example-removal` cannot run `db:test` (no live database), so a marked SQL block would have had no guard in either direction.

### 2026-07-30 — Unauthenticated cold start is measured in Playwright

**Unauthenticated cold start is measured in Playwright, closing the gap that dropping `/` from lhci opened.** `e2e/performance.spec.ts` loads `/` with `/api/session` mocked unauthenticated, waits for the redirect and the sign-in form, and asserts LCP ≤ 2.5 s. The measurement is valid across two URLs because `AuthBoundary` uses `router.replace()` — a soft navigation, so the document survives and LCP neither resets nor rebases its timestamps. That is not an assumption: instrumenting the observer showed exactly two candidates per run, the pre-redirect shell text at ~132–144 ms and the sign-in subtitle at ~276–296 ms, so the winning entry is post-redirect content timed from the original navigation. Measured 268–408 ms across 19 local runs. **The budget is the 2.5 s field number, not a local calibration** — the same constant already used by the authenticated cold-launch test and the budgets list, so it carries one meaning everywhere; a machine-fitted threshold would read as a tighter guarantee than a shared ubuntu runner can keep. Tighten only against numbers measured on that runner. Note the ~6× headroom is against an unthrottled Playwright profile and is not comparable to a throttled Lighthouse number for the same journey (the retired lab figure was ~3.1–3.4 s). Re-adding `/` to `lighthouserc.cjs` once it is a real page (see `START_NEW_APP.md`) adds lab-profile coverage but is no longer the only way to measure this.

### 2026-07-29 — experimental.inlineCss measured and rejected

**`experimental.inlineCss` was measured and rejected — do not re-attempt on LCP grounds.** `/sign-in` LCP is ~96% render delay (TTFB 454 ms · load delay 0 · load time 0 · **render delay 1566 ms**), and the LCP element is the static subtitle `<p>` in `src/app/(public)/sign-in/page.tsx` — text already present in the prerendered HTML, with no image or webfont to fetch. Inlining the stylesheet removes the only render-blocking resource, and it does improve **FCP by ~70 ms** (767 → 696 ms on `/sign-in`, 773 → 704 ms on `/`; both arms n=5, same session). **LCP does not move:** 2166 → 2161 ms, inside the ~55 ms within-batch spread. The LCP paint is gated by main-thread script evaluation (234 ms, of which `webpack-*.js` is 143 ms of scripting), not by stylesheet arrival — the 154 ms Lighthouse charges the CSS was never the binding constraint. `/` LCP also measured 274 ms worse (3144 → 3418 ms); the distributions overlap (3090–3259 vs 3172–3597) so that is suggestive rather than established, but there is a real mechanism: `/` client-redirects to `/sign-in`, so inlining ships the full 15.6 KiB of CSS in **two** documents instead of letting the second reuse the cached stylesheet. Not adopted — FCP is not a budgeted metric here, and a permanent `experimental.` flag in the template is not worth an unbudgeted gain against a possible regression on a budgeted one. The remaining `/sign-in` LCP lever is that main-thread work, which is a profiling job, not a config flag.

### 2026-07-28 — browserslist is documentation, not an optimization

`browserslist` in `package.json` records the supported floor (Chrome/Edge 111, Firefox 128, Safari/iOS 16.4) — the same floor Tailwind v4 already imposes through its generated CSS, so it excludes no browser that could render the app. **It is documentation, not an optimization:** builds before and after were byte-identical (161.8 KiB gzip across 12 chunks; `polyfills-42372ed130431b0a.js` unchanged at 112594 B). Next 16 emits its `nomodule` polyfill chunk regardless. Do not cite this key as a bundle-size measure. **Root cause of the Lighthouse `legacy-javascript` flag, measured 2026-07-29:** the flagged shims in root-shell chunk `838` (`Array.prototype.at/flat/flatMap`, `Object.hasOwn`, `Object.fromEntries`, `String.prototype.trimStart/trimEnd`) are webpack module `8456`, byte-for-byte `next/dist/build/polyfills/polyfill-module.js` — Next framework code injected unconditionally into the client entry, **1380 bytes raw**, not SWC transpilation output. No compiler target removes it; the audit's "~12 KiB" is its whole-chunk savings estimate, not the polyfill's size. The es-shims in the lockfile (`string.prototype.trimstart`, `object.fromentries`, `array.prototype.flat`) are dev-only via `eslint-config-next` and are not in the client bundle. Removing this would mean aliasing a framework-internal path in webpack config — unsupported, and out of proportion to a sub-KiB gzip saving. Do not re-attempt on bundle-size grounds.

### 2026-07-28 — Supabase preconnect in the root layout

The root layout preconnects to the `NEXT_PUBLIC_SUPABASE_URL` origin. Every client-side Supabase call sits behind a dynamic import (session-provider's auth listener and sign-out, the sign-in form's submit), so the browser would otherwise discover the origin only when the first auth request fires; the preconnect warms DNS/TLS at first paint instead. `crossOrigin="anonymous"` is required — supabase-js issues CORS fetches without cookies, and a mismatched mode opens a connection the real request cannot reuse. The origin is baked at build time, like every other `NEXT_PUBLIC_` value. This targets auth-request latency, not LCP. `preconnectOrigin` (`src/lib/env/preconnect-origin.ts`) suppresses the tag for `localhost`/`127.0.0.1`/`[::1]` and the `example.supabase.co` placeholder: a local stack has no DNS/TLS handshake to save, and the placeholder host does not resolve, so the browser would open a connection the real request can never reuse. It is a pure function so the rule is unit-testable without touching the module-scope `clientEnv` parse.
